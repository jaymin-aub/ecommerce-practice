# Commit Message Generator Skill (`/commit`)

This skill reviews pending git changes, verifies security hygiene, and suggests a clean, standardized, single-line conventional commit message.

> **Read-Only Invariant:**  
> This skill is strictly **read-only**. It must **never** execute `git commit`, `git add`, or make changes to the repository. It only inspects the diff and outputs the recommended commit command for the user to review and run.

---

## Execution Workflow

Whenever `/commit` is invoked, execute these steps in order:

### Step 1: Inspect Changes
1. Run `git status -s` to list all modified, added, deleted, or untracked files.
2. Run `git diff --cached` to review staged changes. If nothing is staged, run `git diff` to review unstaged modifications.

### Step 2: Sensitive Data & Secret Scan (Safety Gate)
Before generating any message, inspect the diff for sensitive information:
- Check for `.env`, `.env.*`, `.pem`, `.key`, `id_rsa`, `.p8`, credentials, or secret tokens.
- Scan diff lines for hardcoded passwords, database connection strings with credentials, private JWT secrets, API keys, or tokens.
- **If sensitive content is detected:**
  - **HALT and WARN:** Immediately emit a prominent warning identifying the exact file and lines containing sensitive data.
  - Advise the user to unstage or remove the secrets before committing.

### Step 3: Scope & Atomicity Evaluation
- Evaluate whether the diff represents a single cohesive logical change or multiple unrelated concerns:
  - **Single concern:** (e.g. only backend CORS configuration, or only documentation updates).
  - **Multiple concerns:** (e.g. backend CORS dependencies + documentation templates + agent skills mixed together).
- **If multiple distinct changes are bundled together:**
  - Flag this explicitly to the user:
    > *"I noticed multiple distinct changes in this diff ([Concern A] and [Concern B]). Would you prefer to commit them separately in atomic commits, or combine them into one?"*
  - Provide both:
    1. The split commit options (recommended for atomic git hygiene).
    2. The combined single commit option.

### Step 4: Generate Clean Conventional Commit Message
Adhere strictly to the **Conventional Commits** specification:

#### Format:
```
<type>(<scope>): <subject>
```

#### Rules:
1. **Single Line Only:** Do not include a commit body, multi-line bullet points, or footer descriptions unless explicitly asked.
2. **Zero AI Indicators:** Never include `Co-authored-by:`, `Generated by AI`, `Assisted by`, or any reference to AI models, agents, or LLMs. The commit must read as if written directly by a human engineer.
3. **Imperative & Lowercase:** Use present imperative tense (e.g., `add`, `fix`, `refactor`, `update`, not `added`, `fixes`, `refactored`).
4. **Length Limit:** Keep the entire message under 72 characters.
5. **No Ending Punctuation:** No trailing period or punctuation.

#### Allowed Types:
- `feat`: A new feature for the user or API.
- `fix`: A bug fix.
- `docs`: Documentation-only changes (`docs/`, `*.md`).
- `refactor`: Code change that neither fixes a bug nor adds a feature.
- `perf`: Code change that improves performance.
- `test`: Adding missing tests or correcting existing tests.
- `chore`: Maintenance, config changes, build scripts, package dependencies.
- `style`: Formatting, missing semicolons, whitespace (no code logic changes).

#### Common Scopes:
- `backend`, `frontend`, `shared`, `auth`, `cart`, `product`, `deps`, `workflow`, `skill`

---

## Output Format to the User

Present the recommendation clearly:

```markdown
### Proposed Commit

```bash
git commit -m "<type>(<scope>): <subject>"
```

*(If multiple concerns detected, present the atomic breakdown and ask the user's preference).*
```
